# Задача #10: передача для валидации на второй неделе

Рабочий кандидат: `prompts/literary-analysis-v5.txt` + модель `GigaChat-2-Max`.
Результаты: `calibration/results-final.json`; пять основных примеров для
прикрепления к задаче: `calibration/five-tests.json`. Полный читаемый документ:
`docs/prompt-calibration-report.md`.

Это материалы для передачи Данилу. Сообщение ему и комментарий в GitHub
ещё не отправлены.

## Контракт

Сохранены поля mock-бэкенда напарника: `term`, `definition`, `explanation`,
`examples`. Расширенная схема с отдельными evidence/type/uncertainty оказалась
нестабильной в проверенных прогонах, поэтому не предлагается как основной
контракт. Контекст и ограничения объясняются внутри `explanation`.

`calibration/backend-response.schema.json` задаёт точные поля и типы:
объект, четыре обязательных поля, никаких дополнительных ключей;
непустые строки; `examples` — ровно две непустые строки.
Это строже текущего mock `ExplainResponse`, где массив примеров необязателен.
Изменение ограничений необходимо согласовать при интеграции.

## Приём ответа в бэкенде

1. Передавать текст и контекст как сериализованный JSON в user-сообщении;
   системный промпт держать отдельно. Не конкатенировать текст с инструкциями.
2. Запрашивать `response_format.type=json_schema`, `schema` и `strict=true`
   для поддерживаемой модели. Во всех испытаниях этот параметр отправлялся;
   не считать его заменой локальной валидации: на GigaChat и GigaChat-2 ответы
   всё равно нарушали схему и даже синтаксис JSON.
3. Проверять `finish_reason == stop`, лимит ответа, затем строго разбирать
   `message.content`. Отклонять Markdown, текст вокруг объекта, дубли ключей,
   NaN/Infinity, массив или JSON-строку вместо объекта.
4. Валидировать по схеме и дополнительно сравнить `term` с выделенным текстом.
   Для Pydantic: строгие типы, `extra='forbid'`, проверки длины строк/массива.
5. При ошибке — один повторный запрос с конкретной ошибкой валидатора и
   исходным вводом. Не анализировать текст ошибки как новый литературный ввод.
6. Если повтор снова невалиден — вернуть контролируемую ошибку (например,
   `analysis_unavailable`), а не отдавать строку модели клиенту с HTTP 200.
   Код HTTP и формат ошибки согласовать в API-контракте.

Наша проверка гарантирует только, что **принятый** результат корректно
разбирается и имеет нужные поля. Ни промпт, ни один прогон не гарантируют,
что модель всегда ответит, или что её объяснение семантически верно.

Для production нужны таймауты, контролируемые повторы для сетевых ошибок,
обновление OAuth-токена, лимиты длины ввода и расхода токенов. Калибровочный
скрипт предназначен для небольшого последовательного прогона, не заменяет
production-клиент GigaChat.

## Проверка смысла

Схема не определяет, правильно ли понята идиома, естественны ли примеры,
или не выдумала ли модель возраст персонажа. Это отдельная оценка.
Перед широким использованием нужны новые примеры, не участвовавшие в
калибровке: реальные отрывки с проверенными источниками, сленг,
ирония без очевидных подсказок, большие контексты и повторные прогоны.
В текущем наборе восемь авторских учебных абзацев; это не слепой бенчмарк
и не цитаты из опубликованных произведений.

## Повторный запуск (PowerShell)

Из каталога `C:\lov3waste\NEXA-T\gigachat-prompt-calibration`:

```powershell
& "C:\Users\vladi\.cache\codex-runtimes\codex-primary-runtime\dependencies\python\python.exe" -X utf8 .\calibration\run_calibration.py --env-file "C:\lov3waste\NEXA-T\literature-reader-backend\.env" --structured
```

Вместо встроенного Python можно использовать любой Python 3.10+.
Новых pip-зависимостей нет. Ключ читается из существующего локального `.env`;
сертификат разрешается относительно его папки. Ключи и OAuth-токены в
отчёты не записываются. Новый прогон сохраняется в `results-new.json`,
не перезаписывая исходные результаты. Повторные запросы расходуют API-токены.

Офлайн-проверки:

```powershell
python -m unittest discover -s tests -v
```

Документация структурированного вывода:
https://developers.sber.ru/docs/ru/gigachat/guides/structured-output
